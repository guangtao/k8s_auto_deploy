# 打包与版本规则

适用于 k8s-deploy 离线部署包。参考 monitor-install 的打包规则制定：**部署包有自己的版本号，每次给现场出新包都要升版本号，出包后自动上传 OSS**。

## 1. 版本号

- **位置**：仓库根目录 `VERSION` 文件，只有一行 `x.y.z`，例如 `3.1.0`。
- **和 K8s 版本无关**：K8s、Calico、Longhorn、Harbor 等组件版本只作为包内信息记录（`RELEASE.md`、`BUNDLE_INFO.txt`），不进包名。升级 K8s 版本本身也只是一次改动，按下表升部署包版本。
- **包名**：`k8s-deploy-v<VERSION>-<架构>.tar.xz`
  - 例：`k8s-deploy-v3.1.0-amd64.tar.xz`、`k8s-deploy-v3.1.0-arm64.tar.xz`
  - 混合架构包：`k8s-deploy-v3.1.0-amd64-arm64.tar.xz`
  - 包名不带日期、分支和 commit；它们写在包内 `BUNDLE_INFO.txt` 和 `RELEASE.md` 里。

### 1.1 递增规则

| 改动 | 升哪一位 | 例 |
|---|---|---|
| 修 bug、改提示文案、补检查项、调整默认值等小改动 | z（末位） | 3.1.0 → 3.1.1 |
| 新增步骤/组件/功能、新增配置项、镜像或组件升小版本 | y（中位，z 归 0） | 3.1.1 → 3.2.0 |
| 不兼容的改动：配置结构变化（旧 `render_config.py` 不能直接用）、部署流程变化、K8s 跨小版本升级（如 1.33 → 1.34） | x（首位，y、z 归 0） | 3.2.0 → 4.0.0 |

- **会进部署包的改动都要升 `VERSION`**：`deploy.sh`、`scripts/`、`template/`、`images/` 镜像清单、默认配置。
- **只改文档**（`*.md`、`docs/`）可以不升。
- 同一天连续多次提交、中间没出过包，可以合并成一次升级；但**出包前 `VERSION` 一定要比上一个已发布的包高**。
- 只在 dgt 分支上改 `VERSION`，通过合并带到其它分支。
- **已经发布的版本号不能复用**：同名包已在 OSS 上，出包会被拒绝（见第 3 节）。

### 1.2 每次升版本要同时做的事（同一次提交）

1. 改 `VERSION`。
2. 写发布说明 `docs/releases/v<新版本>.md`（模板见 `docs/releases/README.md`），并加到 `docs/releases/README.md` 的版本列表里。
   - 给现场和客户看：本版变化（新增/变更/修复）、怎么升级、注意事项。
   - 组件版本表不用手写，出包时自动追加。
   - 已经出过包的版本，发布说明只能补充注意事项，不能改「本版变化」；有新改动就升新版本。
3. 在 `CHANGELOG.md` 更新"当前最新版本"，并在记录里追加一条（新的在上）。

## 2. 出包（打包机 47.86.198.13）

```bash
cd /k8s-deploy
git pull
git log --oneline -1                       # 确认是要出包的那次提交
cat VERSION                                # 确认版本号已升

bash deploy.sh bundle -a amd64             # x86 现场
bash deploy.sh bundle -a arm64             # ARM 现场
bash deploy.sh bundle -a amd64,arm64       # 混合集群
# 出包时间长（xz 压缩约几十分钟），建议后台跑：
nohup bash deploy.sh bundle -a amd64 > /root/bundle-amd64.log 2>&1 &
```

出包前会先检查，任意一项不通过就不出包：

| 检查 | 不通过时 |
|---|---|
| `VERSION` 格式为 x.y.z | 修正 `VERSION` |
| `docs/releases/v<版本>.md` 存在 | 补写发布说明并提交 |
| 产出目录没有同名包 | 先升 `VERSION`；确认是同一版本重打，加 `--overwrite` |
| ossutil 可用、能访问上传目录 | 安装 / 配置 ossutil；只想本地出包加 `--no-upload` |
| OSS 上没有同名包 | 先升 `VERSION`；确认是同一版本重传，加 `--overwrite` |
| 离线包校验（verify-pkg）通过 | 补齐缺失的镜像或文件 |

有未提交的代码修改时会给出警告，并按当前文件出包。正式出包前先提交，包里记录的 commit 才和实际内容一致。

### 2.1 产物

| 文件 | 内容 |
|---|---|
| `k8s-deploy-v<版本>-<架构>.tar.xz` | 代码 + 该架构的离线包，解压即可部署；用 `--split 4G` 时为 `.part00`、`.part01` … |
| `k8s-deploy-v<版本>-<架构>.sha256` | 校验值，现场 `sha256sum -c` |
| `k8s-deploy-v<版本>-<架构>-RELEASE.md` | 发布说明 + 自动生成的组件版本表（包内也有一份 `RELEASE.md`） |
| `k8s-deploy-v<版本>-<架构>-DEPLOY.md` | 现场部署手册（包内也有一份 `DEPLOY.md`） |

## 3. 上传 OSS

- **上传目录**：`oss://cyberdownland/k8s_install/`
- **自动上传**：自检通过后，出包脚本会上传安装包（或全部分卷）、`.sha256`、`-RELEASE.md` 和 `-DEPLOY.md`，然后逐个核对 OSS 上确实存在。
- **打印下载信息**：上传完成后打印每个文件的下载地址和 SHA256，直接填进部署指南的下载表格。

  下载地址格式：
  ```
  http://172.88.1.51:8000/public/sign?bucket_name=cyberdownland/k8s_install&package_name=<文件名>
  ```
  如果下载服务换了地址，用环境变量 `DL_PREFIX` 覆盖。

**打包机准备（只做一次）：**
- 安装 ossutil，v1、v2 都可以。PATH 里叫 `ossutil` 或 `ossutil64` 均可，也可以用环境变量 `OSSUTIL=/path/to/ossutil` 指定。
- 执行 `ossutil config`，配置 AccessKey 和地域。
- **AccessKey 只存在打包机上，不进仓库。**

**相关选项：**

| 选项 | 作用 |
|---|---|
| `--no-upload` | 只在本地出包，不上传 |
| `--oss-dest oss://bucket/dir/` | 上传到其它目录（也可用环境变量 `OSS_DEST`） |
| `--overwrite` | 同一版本重打、重传时覆盖本地和 OSS 上的同名包 |

上传失败时，包仍留在本地产出目录，按提示手工补传：
```bash
ossutil cp -f /root/<文件> oss://cyberdownland/k8s_install/
```

## 4. 发布后

1. 把下载地址和 SHA256 填进部署指南的下载表格。
2. 内网 git 同步（在能同时访问 GitHub 和内网 GitLab 的机器上执行）：
   ```bash
   git fetch https://github.com/guangtao/k8s_auto_deploy.git dgt
   git push origin FETCH_HEAD:dgt
   ```
3. 现场查看包的版本：用包名里的版本号，或者解压后执行 `cat k8s-deploy/BUNDLE_INFO.txt`，可以看到分支、commit 和出包时间。

## 5. 现场补丁

现场临时补丁（只替换个别脚本的 tar 包）**不算发布**，不升版本号。补丁里包含的修改，必须进入下一个正式版本的发布说明。

补丁里**不要放 `scripts/render_config.py`**，否则会覆盖现场已经改好的配置。
